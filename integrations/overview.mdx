Bruno integrations let you serve your API documentation from inside your own application, on a route you choose.

Install one package, point it at the Bruno collection that already lives in your repository, and your app gains a documentation page:

```text
myapp.com/api/users    → your API
myapp.com/api/orders   → your API
myapp.com/docs         → your Bruno API docs
```

The docs run in the same process as your API, behind the same authentication, and ship with the same deployment.

<Info>
  Integrations are in **beta**. Express, Fastify, and NestJS are supported today, with FastAPI and Django planned. Option names may still change before the stable release.
</Info>

### The collection already lives with your code

Most teams keep their Bruno collection in the same repository as the service it tests:

```text
payment-service/
├── src/
│   └── server.js
├── tests/
├── collection/
│   ├── opencollection.yml
│   ├── Create Payment.yml
│   ├── Get Payment.yml
│   └── environments/
│       ├── local.yml
│       └── production.yml
└── package.json
```

The collection is reviewed in the same pull requests as the code and versioned in the same commits. Serving it as documentation turns that existing artifact into a published API reference:

```text
collection/  →  your app  →  /docs  →  API documentation
```

Both collection formats are supported: the `.bru` format and the OpenCollection `.yml` format.

## How it works

There are two pieces.

**The server package** runs inside your app. It reads the collection from disk once at startup, applies your environment and tag filters, and serves the finished document along with a small HTML page.

**The docs renderer** runs in the browser. It is loaded from Bruno's CDN and draws the documentation, including search, the environment switcher, and the interactive playground.

```text
SERVER SIDE                          BROWSER SIDE

collection/
    ↓
Express / Fastify / NestJS
    ↓
filter + assemble document
    ↓
serve /docs  ─────────────────────→  Bruno docs renderer
                                          ↓
                                     API documentation
```

Because the renderer is loaded from the CDN, the server package stays small and readers need network access to `cdn.usebruno.com`.

## Configuration

Every framework package accepts the same options object. The options fall into two groups, and the difference matters.

### Server options

These decide **what data leaves your server**.

| Option         | Type                                       | Default  | Description                                                                                               |
| -------------- | ------------------------------------------ | -------- | --------------------------------------------------------------------------------------------------------- |
| `url`          | `string`                                   | required | Path to the collection folder or to a single bundled `collection.yml`, resolved relative to your app entry file |
| `route`        | `string`                                   | `/docs`  | Where the documentation is mounted                                                                        |
| `environments` | `{ include?: string[], exclude?: string[] }` or `'*'` | none     | Which environments are published. Absent means none; `'*'` means all                                      |
| `tags`         | `{ include?: string[], exclude?: string[] }` | none     | Which requests are published, matched against request tags                                                |

### UI options

These decide **how the documentation looks**. They are passed through to the renderer under the `ui` key and never affect what data is sent.

| Option              | Type      | Default             | Description                                              |
| ------------------- | --------- | ------------------- | -------------------------------------------------------- |
| `theme`             | `string`  | `light`             | Default theme                                            |
| `pageTitle`         | `string`  | `API Documentation` | Browser tab title                                        |
| `logo`              | `string`  | none                | Logo in the docs header, as a URL or data URI            |
| `favicon`           | `string`  | none                | Tab favicon                                              |
| `gitCollectionUrl`  | `string`  | none                | Repository URL behind the **Open in Bruno** button       |
| `showThemeSwitcher` | `boolean` | `true`              | Show or hide the theme switcher                          |
| `customCss`         | `string`  | none                | Stylesheet that overrides the default styles             |
| `proxyUrl`          | `string`  | none                | CORS proxy for playground requests                       |

A complete example:

```js
apiDocs({
  url: './collection',
  route: '/docs',
  environments: { include: ['production'] },
  tags: { include: ['public'] },
  ui: {
    theme: 'dark',
    pageTitle: 'Payments API',
    logo: '/logo.svg'
  }
})
```

## Filtering is deletion, not hiding

Filters are applied on the server, before the document is sent. An excluded environment's values and an excluded request's auth details are never written into the response at all, so a reader cannot recover them from the page source.

```text
collection → server filters → only published content → browser
```

Two rules are worth remembering:

- **Environments are opt-in.** If you do not set `environments`, none are published. Use `'*'` for all, or name the ones you want.
- **Exclusion wins.** If a request matches both an include tag and an exclude tag, it is left out.

<Warning>
  Treat the published document as public to anyone who can reach the route. If an environment holds production credentials, do not include it.
</Warning>

## A broken setup will not take down your app

If the collection path is wrong, a file is unreadable, or an option is not recognized, the app still boots. The error is logged at startup and the docs route serves the error message instead of the page. Your API keeps running.

Everything else is decided at startup too. The collection is read and filtered once, and each request after that is served from memory with an ETag, so the docs route adds no file system work to your running server.

## Prefer a standalone file?

If you do not want the docs inside your app, Bruno can build a single self-contained HTML file from the same collection instead. That file needs no server and can be hosted anywhere.

- [Generate documentation in the app](/html-docs/generate) using **Generate Docs** in Collection Settings
- [Generate it from the CLI](/bru-cli/runCollection#generate-api-documentation) in a release or CI pipeline
- [Deploy and share the file](/html-docs/deploy)

Both paths render the same documentation from the same collection. Use an integration when the docs should live with the app and follow its authentication, and use the generated file when you want something you can hand over or host separately.
